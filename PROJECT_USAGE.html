Usage & Architecture Guide

A leakage-audited data pipeline that turns nine years of public Binance 15-minute candles into a Colab-ready dataset, trains a small recurrent network on it, and serves that network to two live dashboards. This document is the whole project: what it is, how the pieces fit, what it measured, and exactly how to run every part of it again by hand.

No profitability or trading-edge claim is made anywhere in this project.

Every number below is a measurement on one historical test period, printed next to the naive baseline it has to beat. Nothing here is investment advice. There is no backtest — fees, slippage, funding and regime change all sit between a directional call and a P&L. A directional accuracy above 33% on a three-class problem is not evidence of a profitable strategy. Read the macro-F1 and the per-class recalls, not the headline accuracy.

01

What this project is — and is not

The scope boundary is deliberate. Almost everything the project refuses to do is a thing that would have made its numbers look better.

It is
  • A data pipeline. It downloads the full public BTCUSDT 15-minute history from Binance, validates it, engineers features, builds targets, splits it chronologically, scales it, and writes a dataset.
  • Explicitly leakage-audited. 24 automated checks re-run the real feature, target, scaler and threshold code against deliberately corrupted data and assert that nothing looks forward in time.
  • Honest about gaps. Missing candles are reported and segmented around. They are never interpolated or forward-filled.
  • Trained, and served. A 3-seed GRU ensemble is trained on the full split, then read by a terminal dashboard and by a React dashboard over a JSON/SSE API.
It is not
  • A trading system. No order execution, no risk controls, no position sizing, no scheduler. Both dashboards read the market; neither can act on it.
  • A backtest. Notebooks 04 and 05 contain an intentionally empty scaffold describing what would have to be built. No backtest result is produced or claimed.
  • A performance claim. One asset, one interval, one venue, one test period.
  • A service. The API is bound to localhost, has no authentication and is documented as a local research tool.

How the dataset is built

Every number in this section was measured by running the code on the real Binance data.

A real trap this code handles

Until 2024-12 the Binance kline open_time is in milliseconds (13 digits). From 2025-01 it is in microseconds (16 digits). Both are normalised to timezone-aware UTC on load. Getting this wrong shifts every recent timestamp by a factor of 1000 and silently destroys the split.

4.2 · Cleaning, gaps and the continuity policy

The rule: a missing candle is never fabricated. No reindex-and-interpolate, no forward-filled prices, no synthetic candles. If the exchange did not publish a candle, this project does not invent one.

Instead, every discontinuity in the 15-minute grid starts a new segment. Two things may never cross a segment boundary: a sequence window (the 64 candles fed to the model) and a target (a future return measured across missing candles). An honest gap is a small loss of data; a fabricated candle is a lie the model will happily learn from.

Measured continuity report over the full history.

That last row matters. Dropping a row — an unusable feature NaN, or a gap-crossing target — makes two non-adjacent candles neighbours in the frame, and the inherited segment_id would not notice. pipeline.py therefore rebuilds segment ids from the surviving timestamps, turning 24 holes that existed only because of dropped rows into hard boundaries.

4.3 · The 49 features

Two rules govern every feature:

  1. Backward-looking only. Every feature at row t uses rows ≤ t. All primitives are trailing: .shift(k) with k ≥ 1, trailing .rolling(), recursive .ewm(). This is not asserted, it is proven — audit check 1 corrupts every row after a cut point and confirms the features before it are bit-for-bit unchanged (measured deviation: exactly 0.000e+00).
  2. No absolute price level. BTC ranges from roughly $4,000 to over $100,000 across this period. A raw price input would let the model memorise which regime it is in rather than learn behaviour. Every price expression is a return, a ratio, a percentage distance or a volatility.
Group N Contains

volatility 6 rolling std of 1-bar returns, ATR %, realised volatility
trend 6 EMA-20/50/100 distances, slope ratios, price-vs-EMA normalised by ATR
momentum 4 RSI-14 (normalised), MACD histogram and signal relative to price
bollinger 4 band position, width relative to price, distance to each band
volume 5 volume vs. its 16- and 96-bar averages, z-score, regime ratio

Two features were deliberately excluded

body_pct duplicates return_1 with a correlation above 0.999 in a 24/7 market — a duplicate is not neutral, it silently doubles that direction's weight in any distance-based model. buy_pressure is an affine transform of taker_buy_ratio, which is already a feature. Both exclusions are documented at the bottom of features.py.

4.4 · Targets: returns and direction labels

The return target is a percentage, not a price — prices are non-stationary and unbounded; returns are comparable across the whole history.

future_return_h[t] = 100 * ( close[t+h] / close[t] - 1 )      [percent]

h = 1 → 15m    h = 2 → 30m    h = 3 → 45m
h = 4 → 60m    h = 5 → 75m    h = 6 → 90m

These six columns are the only place future data is touched, and none is ever fed back into a feature — audit check 16 asserts that no target column appears among the model inputs. If close[t+h] lies in a different segment than close[t], the target is set to NaN rather than silently measuring across missing candles; 636 targets were invalidated this way.

The direction label bins that return using train-only quantiles, frozen:

0 = DOWN      return <  lower_threshold
1 = NEUTRAL   lower_threshold ≤ return ≤ upper_threshold
2 = UP        return >  upper_threshold
Measured thresholds — the central 40% of the TRAIN return distribution, per horizon.
Horizon Lower Upper
15m −0.1033% +0.1087%
30m −0.1389% +0.1491%
45m −0.1634% +0.1796%
60m −0.1841% +0.2034%
75m −0.2045% +0.2288%
90m −0.2220% +0.2505%
The most important table in this document

The thresholds give 30 / 40 / 30 on train by construction. Applied unchanged to the test period they give roughly 24 / 54 / 22. That is a genuine distribution shift between the two eras — the 2025–2026 market spent more time inside small 15-minute moves than the 2017–2024 market did. No amount of modelling removes it. The consequences:

  • A model that always predicts NEUTRAL scores about 54% accuracy on test while being completely useless.
  • Macro-F1 is the honest headline metric here. Accuracy is not.
  • A model well calibrated on validation may still be miscalibrated on test purely because the class priors moved.

4.5 · The activity target — why it is the one that works

The direction head asks "which way?", where the sign of a 15-minute move is close to unpredictable. The activity head asks a different question:

absr[t]               = | 100 * ( close[t] / close[t-1] - 1 ) |     [percent]
forward_absmove_h[t]  = mean( absr[t+1 .. t+h] )                     FUTURE
reference_absmove[t]  = mean( absr[t-95 .. t] )                      PAST — 24 hours
regime_ratio_h[t]     = forward_absmove_h[t] / reference_absmove[t]

label = ACTIVE (1)  if regime_ratio_h[t] > tau_h,  else QUIET (0)

Dividing by the sample's own trailing activity makes the label self-normalising: both sides of the ratio are mean absolute returns of the same asset in the same units, so the class balance does not drift when the price level or the overall volatility regime changes. Measured: train 50.0% ACTIVE, validation 50.6%, test 49.6% — a train→test drift of 0.39 pp, against the direction thresholds' 6 pp. And because the classes are 50/50 by construction, 0.50 is the baseline: there is no majority class to hide behind.

tau_h is the median of the ratio over the TRAIN split only, then frozen:

Horizon Ratio threshold Class rule
15m 0.7390 ratio > 0.7390 → ACTIVE
30m 0.8090 ratio > 0.8090 → ACTIVE
60m 0.8528 ratio > 0.8528 → ACTIVE
90m 0.8724 ratio > 0.8724 → ACTIVE

4.6 · Sequence geometry — the "block + offsets" contract

Read this one before touching any array

One sample is:

X : (n_samples, 64, 49)     64 candles × 49 features = 16 hours of context
y : (n_samples, 6)          six future percentage returns
d : (n_samples, 6)          six DOWN/NEUTRAL/UP labels
r : (n_samples, 4)          four QUIET/ACTIVE labels

sample k uses 2D rows [ starts[k] , starts[k] + 63 ]
its target is the target of ROW starts[k] + 63  — the LAST candle in the window

Why the 3D tensor is never stored. A fully materialised (312,165, 64, 49) float32 tensor is 3.92 GB, while the equivalent 2D matrix is about 60 MB. The 3D tensor is therefore produced as a zero-copy sliding-window view and materialised one batch at a time by SequenceBatcher.

The part that is easy to get wrong. Windows that would straddle a data gap are excluded, which leaves holes in the sequence of window-start indices. Consequently:

  • X_train.npy is a contiguous 2D block, not one row per sample.
  • starts_train.npy holds the window-start offset of each sample inside that block.
  • Sample k is X[starts[k] : starts[k] + LOOKBACK] — never X[k : k + LOOKBACK].

On this dataset starts_train has 218,515 entries but the block has 221,413 rows, and the offset sequence contains 43 discontinuities. Slicing X_train[k : k+64] would silently splice across one of those holes and fabricate a window spanning missing market data — the precise failure this project exists to avoid.

The offsets are block-relative, not global. starts_train[0] == 0, and likewise starts_val[0] == 0. Offsets from two different splits are therefore not comparable; subtracting one from the other is meaningless. To relate two splits in time, use timestamps_*.npy, which holds each sample's target time in absolute UTC. The same applies to y_*.npy, y_dir_*.npy and timestamps_*.npy: they already hold exactly one row per sample — do not apply a [LOOKBACK-1:] offset to them.

4.7 · The chronological split and the purge

Time order is never shuffled. Training on the future to predict the past is the single most common way to produce a financial ML result that looks brilliant and is worthless. The split is a strictly monotonic slice of a time-ordered array: train → purge → validation → purge → test.

Split Samples Period (UTC)
train 218,515 2017-08-23 21:45 → 2024-01-15 02:00
validation 46,824 2024-01-15 19:45 → 2025-05-17 13:30
test 46,686 2025-05-18 07:15 → 2026-09-16 14:30
purged 140 70 samples at each boundary
Valid windows 312,165 from 315,000 candidates — 2,835 excluded
Why the purge is 70 samples and not 6

A sample's window occupies 64 candles, and its label is resolved from candles up to 6 further past the end of that window. So the last training sample's label is computed from rows [start+63, start+69]. For no training label to be resolved from any candle inside the validation feature window, the separation must exceed LOOKBACK − 1 + HORIZON_MAX = 69 rows. Purging only HORIZON_MAX = 6 would leave a 57-row overlap in which training labels are computed from candles the validation inputs also summarise.

PURGE_SAMPLES = LOOKBACK + HORIZON_MAX = 70. Measured separation: 71 rows = 1,065 minutes at both boundaries, against a 70-row minimum. The pipeline asserts this invariant and refuses to run if it is violated, so a future change to LOOKBACK or HORIZONS cannot silently break it.

Validation vs. test. Validation is for choosing the architecture, the hyperparameters and the early-stopping epoch. Test is touched exactly once, at the end. If you find yourself tuning against the test set, it has stopped being a test set.

4.8 · Scaling — fitted on the training split only

Fitting a scaler on everything lets the mean and standard deviation of the test period influence how the training data is represented. That is leakage, and it is a particularly sneaky kind because the code still runs and the scores still look fine.

  • StandardScaler, fitted on the rows that make up the training windows and nothing else: rows [0, 221,413).
  • That range ends strictly before the first validation feature row (221,420). The last training label is resolved from candles up to row 221,418 — 1 row of clearance, tight by construction, and audit check 11 re-verifies it.
  • The same frozen scaler is applied to validation and test, then saved to data/final/scaler.pkl and loaded, never refit, by inference and both dashboards.
  • Scaled values are clipped to ±5σ. 0.329% of training values sit at the clip bounds — a direct consequence of the kurtosis of ≈84. Measured: train max|mean| = 0.0166, mean std 0.9305 (1.0 before clipping).
  • Targets are scaled too, fitted on train only, because MSE gradients on ±0.39% returns are tiny. Raw unscaled returns remain the source of truth in the CSV and in y_*.npy.

Clipping is a numerical-stability choice, and it has a real cost: the largest moves, which are the ones a trader would care most about, are damped. That is stated rather than hidden.

05

How leakage is prevented

Six mechanisms, all verified automatically by python src/audit_leakage.py.

1 · Features are strictly backward-looking

Verified by corrupting all rows after a cut point and asserting the features before it are bit-for-bit unchanged — measured deviation exactly 0.000e+00.

2 · Targets are the only forward touch

And a target that would span a data gap is NaN rather than measured across missing candles.

3 · Missing candles are never fabricated

Every discontinuity starts a new segment; neither a window nor a target may cross one.

4 · Splits are strictly chronological

70/15/15 in time order, never shuffled.

5 · A purge of 70 samples separates the splits

So no training label is resolved from any candle inside the validation or test feature windows.

6 · Scaler and thresholds are train-only

Fitted on the training split and then frozen. The test set never influences either.

The checks come in two kinds: dynamic checks that re-execute the real functions on synthetic data whose future is deliberately corrupted, and static checks on the artefacts the pipeline actually wrote.

06

The model

One shared recurrent trunk, three heads, three seeds averaged.

Input(batch, 64, 49)
→
GRU trunk64 units · dropout 0.25
→
return headlinear · 6 outputs · MSE on scaled returns
+
direction headreshape (6,3) then softmax · weighted CE
+
activity headsigmoid · 4 outputs · binary CE

Why multi-task at all

The direction head regularises the trunk toward representations that are useful for classification, while the return head keeps the magnitude information the direction labels throw away. The activity head adds a third question that is genuinely predictable, and it is the one whose accuracy means something.

Class weighting — a deliberate trade

Trained with a plain cross-entropy the direction head collapses onto NEUTRAL: measured test recall was DOWN 0.19 / NEUTRAL 0.85 / UP 0.21. DIRECTION_CLASS_WEIGHT_STRENGTH = 0.5 interpolates between no weighting and full inverse-frequency weighting, normalised to mean 1 so the effective learning rate does not change. The measured weights are 1.047 / 0.907 / 1.047 per horizon.

This trades accuracy for macro-F1, and the trade was made explicitly: pushing recall into the minority classes necessarily costs some majority-class hits. Accuracy is barely affected either way, and the activity head is the accuracy headline.

What early stopping monitors

The original configuration early-stopped on val_loss = MSE(return) + CE(direction) + CE(activity). The return head has no skill, so most of the early-stopping signal was a head that cannot predict anything drowning out the two that can. The checkpoint metric is instead computed on the validation split by a callback:

selection_score = 0.5 × direction_macro_F1 + 0.5 × activity_accuracy

Both terms live in [0, 1] and both are things the project reports anyway. Measured selection score: 0.5505.

Three seeds, averaged rather than picked

The shipped artefact is not a single winning .keras file. It is a three-member ensemble — gru_s42, gru_s43, gru_s44 — combined by the mean of the per-member softmax probabilities, named in models/inference_bundle.json.

The reason is the seed-to-seed spread: the differences between seeds are within noise, so picking the best one on validation would be selecting on noise. Averaging is the cheapest reliable gain available here — it costs only time, it cannot leak, and it reduces the variance that makes a single-seed score hard to trust.

A bug worth knowing about

An earlier revision applied softmax to the flat 18-vector and reshaped to (6, 3) afterwards. That shares one normaliser across all six horizons, so each horizon's three probabilities summed to ≈1/6 rather than 1, and the head could not express "UP at 15m, DOWN at 90m" independently. Argmax survived it — softmax is monotonic within a group — which is exactly what made it easy to miss. It was caught only by noticing that displayed probabilities did not sum to 1.

The order is now reshape-then-softmax, and build_multi_task_model() asserts the normalisation after building, as does notebook 05. Shapes alone would not have caught it; the assertion is on the values.

7.4 · The confidence floor is a straight loss

The dashboard lets you raise a floor: calls below it display as NEUTRAL. It sounds prudent. It was measured, and on this model it costs macro-F1 monotonically while buying essentially no accuracy.

Floor Test macro-F1 Test accuracy Commits to a direction
0.00 0.4237 0.5282 33.2%
0.38 0.3960 0.5337 24.0%
0.50 0.2469 0.5234 1.6%
0.70 0.2283 0.5202 0.0%
always-NEUTRAL baseline 0.2281 0.5202 0%

The small test-set accuracy bump at 0.38 costs 9 points of macro-F1 to buy 0.25 points of accuracy. The reason: downgrading a weak DOWN or UP call to NEUTRAL removes exactly the scarce thing the model is being measured on — DOWN and UP recall are already the bottleneck, while NEUTRAL is already over-predicted. Removing rare-class calls cannot help a macro-averaged metric.

This does not contradict the calibration table. Calibration says the probability is informative within the model's own argmax calls (test accuracy rises 0.37 → 0.83 across confidence buckets). The floor overrides those argmax calls, and the override is what costs. Both are measurements of different things.

7.5 · How to read any number that comes out of this project

  1. Did it beat the naive zero-return baseline on MAE? If not, it has learned nothing the mean does not already tell you.
  2. Did it beat the majority-class baseline on macro-F1 — not accuracy? On this test set, always-NEUTRAL scores about 54% accuracy while being worthless.
  3. Is it better than XGBoost on the same split? A recurrent architecture that loses to gradient-boosted trees on tabular-ish features is a real and common outcome.
  4. Are the per-horizon numbers coherent? Strong at 15m and 75m but random at 30m is a red flag, not a discovery.
  5. Does the confusion matrix show a collapsed class? A model that never predicts DOWN will have a respectable-looking accuracy and a terrible DOWN recall.
  6. Was the test set touched more than once? If you looked, changed something and looked again, it is now a validation set with extra steps.
What this establishes

16 hours of 15m candles contain some information about both the direction and the volatility of the next 15–90 minutes that a recurrent network can extract — on one test period, under a leakage-audited split. The volatility question is answered well; the direction question is answered poorly but better than chance.

What it does not establish

Profitability. The test period is a single regime, directional recall is low, and no fees, slippage or funding are modelled anywhere. A macro-F1 of 0.42 on a three-class problem, and a volatility classifier that is right 65% of the time, are a long way from a trading edge. Directional accuracy ignores magnitude: a model can be right 55% of the time and still lose money if its correct calls are small and its wrong ones are large.

8.3 · The projection store

The dashed curve is one window: what the model is saying now. On its own that says nothing about whether the projections track the price or merely look plausible once, so every projection is written to SQLite (models/predictions.db, stdlib sqlite3, no new dependency) and read back into the same chart.

  • One row per horizon per head per window, keyed (anchor_ts, horizon, kind). Re-refreshing a window is INSERT OR IGNORE, so it cannot double-count.
  • actual_close is filled in once the target candle prints, so the store is self-contained: prediction and outcome in the same row.
  • The chart line uses the direction head only. The activity head stores expected_pct = 0 by construction, so averaging its rows in would drag the curve towards "no change" and make the model look worse than it is. That would be a bug in the chart, not a finding.
  • A gap longer than 4 candles is drawn as a break. Across an outage the model made no call, and a line spanning it would imply otherwise.
  • --no-record opens the file read-only if it exists and creates nothing if it does not — enforced by SQLite (mode=ro), not only by a guard.

It is local state — gitignored, not a result to read out of the repository.

Symptom Cause and fix

Environment & reproducibility

Deterministic

The entire data pipeline. Download, cleaning, features, targets, split, scaler and thresholds contain no randomness. Re-running python src/pipeline.py on the same raw CSV reproduces the dataset bit-for-bit.

Changing the raw data (a new Binance month) obviously changes the dataset, which is why the metadata records the generation timestamp.

Not deterministic

Model training. Even with seeds fixed, device, kernel selection and reduction order introduce run-to-run variation. A difference of a fraction of a point between two runs means nothing.

Re-run with several seeds before drawing a conclusion from a small gap — which is exactly why the ensemble averages three rather than picking one.

Portability notes worth keeping

  • Timestamps are stored as int64 epoch milliseconds precisely so the .npy files contain no timezone objects and no pickle.
  • pandas 3.0 changed several behaviours this code had to accommodate: pct_change's fill_method removal (returns are computed explicitly), microsecond-resolution tz-aware datetimes (epoch conversions cast through datetime64[ms] rather than dividing a tick count), and the removal of pd.io.common.file_exists.
  • The human-readable CSV is rounded to 8 decimals. The .npy files are not rounded and are the authoritative values.
  • A local run will not reproduce a Colab run exactly even with identical seeds — different device, different kernel selection. Treat small differences as noise, not as a finding.

Limitations and honest caveats

The list the project would rather you read before the results.

Data
  • One asset, one interval, one venue: BTCUSDT 15m on Binance spot. Nothing here demonstrates anything about other assets, timeframes or exchanges.
  • 643 missing candles (0.2019%). Reported and segmented around, never filled. The model has never seen what happened during those windows.
  • Train spans 2017–2024 and test spans 2025–2026 — different market regimes, visibly so in the class balance.
Features
  • 49 features from OHLCV and trade counts only. No order book, no funding rates, no open interest, no on-chain, no macro or news. If the signal lives in data this project does not ingest, no model here can find it.
  • Features are clipped at ±5σ for numerical stability, which damps exactly the extreme moves a trader would care about.
  • Correlated-but-not-identical features were kept where they carried genuinely different information, which affects tree-model importance interpretation.
Modelling
  • Stride-1 windows mean consecutive samples share 63 of 64 candles. The sample count is not the number of independent observations; any confidence interval that treats it as such is wrong.
  • No hyperparameter search is implemented. The defaults are reasonable starting points, not tuned values.
  • No walk-forward retraining and no regime-aware modelling.
Claims
  • No profitability or trading-edge claim anywhere. Every number is a measurement on one historical test period.
  • The return head is reported as failing — documented rather than quietly dropped.
  • The backtest is deliberately unimplemented. The confidence floor is measured to hurt, and exposed as a control, not a tuning knob.
  • The live scorecard is measured, not asserted — but it is a small sample. Do not read a hit rate off twenty calls.
The main weakness is the NEUTRAL bias

Directional recall on test is 0.22–0.29 — better than the 0.18–0.22 measured before the class-weighted loss was introduced, but still missing most directional moves. That was the direct attack on this problem and it helped without solving it; a different neutral band is the obvious next lever. Do not spend that effort on the return head, which has no signal to recover in the first place.

And do not let the activity head's better number migrate into a directional claim. It answers a question about volatility. It is not a trade.

Glossary

Term Meaning in this project
Sample / window 64 consecutive candles (16 h) of 49 features, plus its targets.
Horizon How far ahead a target looks: 15, 30, 45, 60, 75 or 90 minutes (1–6 candles).
Segment A contiguous run of real candles. A new segment starts at every gap, and neither a window nor a target may cross one.
Gap Any discontinuity in the 15-minute grid — a candle the exchange never published.
Purge / embargo The 70 samples removed at each split boundary so no training label is resolved from a candle inside the next split's feature windows.
Block + offsets The storage contract: X_*.npy is one contiguous 2D block and starts_*.npy holds each sample's offset into it.
Direction head The 6 × 3 softmax head predicting DOWN / NEUTRAL / UP per horizon.
Return head The linear head predicting percent return per horizon. Measured to fail.
Activity / regime head The 4 × 2 head predicting QUIET / ACTIVE — "busier than this sample's own trailing 24 hours?"
Macro-F1 F1 averaged over the three direction classes with equal weight. The honest headline direction metric on an imbalanced three-class problem.
Majority-class baseline The score of always predicting the most common class. The floor any direction result must clear.
Naive baseline The score of always predicting the mean return. The floor any regression result must clear.
Confidence floor A setting that downgrades low-confidence directional calls to NEUTRAL. Measured to cost macro-F1 monotonically.
Ensemble The mean of the per-member softmax outputs of the three seed-trained GRUs — averaged, never picked.
Track record The dashboard's own measured hit rate, scored against the frozen train-only thresholds once each call's candle prints.
Projection store models/predictions.db — every projection the dashboard ever made, with the realised close once it exists.
